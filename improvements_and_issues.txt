B-1. GUI β-check uses nominal (20 °C) diameters; iso5167 uses thermal-
     expansion-corrected diameters
     File : ui/gui.py lines 969–974
     Problem: _calculate() computes beta = d_orif / d_int (both at 20 °C)
     and rejects if beta < 0.10 or > 0.80. Inside calc_mass_flow() the
     diameters are corrected for the measurement temperature:
       d_pipe_t  = d_int  * (1 + α_pipe  * (T - 20))
       d_orif_t  = d_orif * (1 + α_orifice * (T - 20))
     and then beta_corrected = d_orif_t / d_pipe_t.
     For an orifice at e.g. 300 °C, the two expansion coefficients
     differ (12.2e-6 vs 16.5e-6), so beta_corrected can drift from the
     nominal beta by ~0.001–0.002. A set of diameters just inside the
     ISO 5167 beta limit (e.g. β = 0.799 nominal for an orifice plate)
     could pass the GUI pre-check but fail or vice versa inside iso5167.
     The user sees no clear explanation.
     Fix: compute the corrected beta in _calculate() and use it for the
     pre-check (or remove the GUI beta pre-check and rely solely on the
     calc_mass_flow() validation).

B-2. Density tolerance is absolute in atm, not relative
     File : constants.py line 15 (DENSITY_TOLERANCE = 5.0e-4)
             formulas/bwrs.py line 162
     Problem: `if abs(p - p_cal) < DENSITY_TOLERANCE` compares an
     absolute pressure error in atm. At low pressures (~0.1 atm) the
     relative tolerance is 0.5 %, which may be too coarse for accurate
     density. At very high pressures (100 atm) it converges 200× faster
     than needed, wasting iterations only when the solution is near.
     Fix: replace with a relative check:
       tol = max(DENSITY_TOLERANCE, abs(p) * 1e-6)
       if abs(p - p_cal) < tol: ...

B-3. BWRS_B0[3] (propane) data value is anomalously large
     File : data/components.py line 36
     Value: 97.313/100 = 0.97313
     Problem: all other BWRS_B0 values are in the range 0.022–0.21.
     Propane's B0 at 0.97 is roughly 5–40× larger than any neighbour.
     If this is a transcription error from Starling 1973 (the original
     may be 9.7313 → /100 = 0.097313), the computed mixture density for
     propane-containing gases will be wrong.
     Fix: cross-check against Starling 1973, Table 3. If the correct
     value is 0.097313, replace `97.313/100` with `9.7313/100`.

B-4. Viscosity parameter ξ uses Tc^6 instead of Tc^(1/6)
     File : formulas/bwrs.py line 180
     Code : thermo.m_csi = (tc_mix ** 6) / math.sqrt(bwr.m_molarMass)
                           / (pc_mix * pc_mix) ** (1/3)
     Problem: the Chapman-Enskog/Nishiumi-Saito viscosity correlation
     defines the mixture parameter as:
       ξ = Tc^(1/6) / (M^(1/2) · Pc^(2/3))
     The code uses Tc^6 (exponent 6 instead of 1/6), producing values
     ~10^11 for typical gases. This makes the high-density correction
     term (VISC_HIGH_A / csi) × ... essentially zero for all practical
     conditions, so the implementation degrades to dilute-gas only.
     The built-in validation tests pass at low pressure (101.325 kPa)
     because the density correction is negligible there, but viscosity
     will be wrong at elevated pressures.
     Fix: change `tc_mix ** 6` to `tc_mix ** (1/6)`.
     Note: verify against Nishiumi & Saito (1975) before changing, in
     case the constant VISC_HIGH_A was intentionally tuned for the
     current formula.

M-1. JSON config/composition files not bundled in PyInstaller spec
     File : BWRS_Calculator.spec line 8 (datas=[])
     Problem: bwrs_comp.json and bwrs_conf.json are opened via relative
     paths (COMP_FILE = "bwrs_comp.json", CONF_FILE = "bwrs_conf.json").
     In a frozen PyInstaller executable, os.getcwd() is typically the
     system temp directory where the bundle extracts, not the directory
     containing the .exe. Loading silently fails (the bare except pass
     in _try_load_config / _try_load_composition hides the error), and
     saving creates files in the wrong location.
     Fix: use sys.executable or __file__ to build a path relative to the
     exe, e.g.:
       BASE_DIR = os.path.dirname(os.path.abspath(sys.executable
                  if getattr(sys, 'frozen', False) else __file__))
       COMP_FILE = os.path.join(BASE_DIR, "bwrs_comp.json")

M-2. CALCULATE runs on the main Tkinter thread
     File : ui/gui.py method _calculate (line 913)
     Problem: _calculate() calls calc_bwr_mixture() (O(N³) for N=35),
     calc_density() (up to 200 bisection steps), calc_viscosity(), and
     calc_mass_flow() all synchronously on the event-loop thread. On a
     slow machine or with a 35-component mixture the UI will freeze
     (unresponsive, greyed-out) for the duration of the calculation with
     no progress feedback to the user.
     Fix: mirror the pattern used for the test runner — disable the
     CALCULATE button, run the computation in a daemon thread, and post
     results back via self.after(0, ...).

M-3. Error messages from calc_mass_flow() leak to stdout in GUI mode
     File : standards/iso5167.py lines 12–22 (print_error)
     Problem: print_error() calls print(...) to sys.stdout. During a
     normal _calculate() call the GUI does not redirect stdout, so error
     messages from range violations appear only in the terminal (if one
     exists) and not in the GUI. The return value of print_error() IS
     propagated back through calc_mass_flow() as an error string and IS
     shown in the GUI via _status_lbl — so the GUI display is correct —
     but the stdout print is redundant and clutters the console.
     Fix: remove the print() call from print_error(); return only the
     string. Callers that need console output can print the returned
     string themselves.

M-4. sys.path.insert(0, ...) hacks are fragile
     Files : ui/gui.py line 13
             tests/validation.py line 4
     Problem: inserting the project root into sys.path at import time
     works only when the CWD or __file__ is within the project tree, and
     only when the module is not already importable via the normal path.
     When launched via main_gui.py (which already inserts the project
     root at line 5), the gui.py insert is harmless but misleading. In
     a PyInstaller bundle, os.path.dirname(os.path.abspath(__file__)) is
     inside the temp-extracted bundle, not the project root.
     Fix: remove the sys.path.insert lines from gui.py and
     tests/validation.py. The project root insert in main_gui.py is
     sufficient when running from source; PyInstaller handles imports
     from the bundle automatically.

M-5. No console entry point at project root level
     Problem: The console UI (when restored) is only reachable by
     running ui/console.py directly, which also requires the sys.path
     hack. There is no main_console.py alongside main_gui.py.
     Fix: add main_console.py mirroring main_gui.py:
       sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
       from ui.console import run
       if __name__ == "__main__":
           run()

N-5. Calorific values use fixed ideal-gas molar volumes, not BWRS
     File : ui/gui.py lines 1100–1105
     Code : hhv_0c  = hhv_mol / MOLAR_VOL_0C
            hhv_15c = hhv_mol / MOLAR_VOL_15C  etc.
     Problem: the code uses constant ideal-gas molar volumes (22.414 L/mol
     at 0°C, 23.645 L/mol at 15°C, 24.055 L/mol at 20°C) rather than the
     BWRS-computed density at those conditions. ISO 6976:2016 mandates
     ideal-gas reference conditions for calorific values, so this is
     technically correct — but there is no comment explaining why BWRS is
     not used here, which can confuse maintainers.
     Fix: add a comment:  # ISO 6976:2016 sec. 5: ideal-gas molar volumes

N-6. bwrs_conf.json hard-coded D=100 / d=50 initial state
     File : bwrs_conf.json
     Problem: the saved configuration has D=100 mm, d=50 mm (β=0.5).
     For a user who never ran the GUI before, these defaults are
     reasonable. But because d=50 mm is the Venturi nozzle orifice lower
     limit (the check in iso5167.py line 109 is `d_orif_t <= 50`, so the
     boundary is included), a Venturi nozzle calculation with these
     exact defaults will be rejected with an orifice diameter error.
     Fix: use d=51 mm or add a note in the UI; or simply verify that the
     default pair passes all nine device types.

N-7. PyInstaller spec has console=False with no fallback error handler
     File : BWRS_Calculator.spec line 33
     Problem: console=False suppresses the Windows console window. Any
     unhandled exception that escapes tkinter's event loop (e.g., an
     ImportError before the window is created) produces no visible output
     to the user — the process silently exits. Until C-1 and C-2 are
     fixed, a user who launches BWRS_Calculator.exe will see nothing.
     Fix: wrap the run() call in main_gui.py with try/except and write
     errors to a log file, or use a messagebox as a last resort:
       try:
           from ui.gui import run
           run()
       except Exception as exc:
           import tkinter, traceback
           tkinter.messagebox.showerror("Startup error", traceback.format_exc())

N-8. Composition tab: FocusOut triggers _update_sum but tab-key between
     fields fires FocusOut immediately
     File : ui/gui.py line 403–404
     Code : e.bind("<FocusOut>", lambda _ev: self._update_sum())
     Problem: every FocusOut triggers a full loop over all 35 entries.
     This is harmless but slightly wasteful. More importantly, the
     closure in the lambda always captures the variable `e` from the
     enclosing scope (last assigned value of `e`), not the specific
     entry being left. This is the classic "closure in a loop" issue.
     In this case the lambda body ignores `e` and only calls
     _update_sum(), so there is no actual bug — but it is a common
     pitfall worth noting for future maintenance.
     Fix: use a default-argument capture if the specific entry is ever
     needed: lambda _ev, _e=e: self._update_sum()

N-9. calc_bwr_mixture skips triples based on xi*xj < 1e-12 but the
     threshold comment is slightly misleading
     File : formulas/bwrs.py line 63
     Code : if xij < _TRIPLE_THRESH: continue
     Comment: "x[i]*x[j]*x[l] ≤ xij < threshold for any x[l]≤1"
     Problem: the comment is logically correct (any x[l]≤1 means
     xi*xj*xl ≤ xi*xj = xij < threshold), but the reader has to think
     twice. Also, with 35 components at even fractions (~0.03 each),
     xi*xj ≈ 0.0009, which is far above 1e-12, so the optimisation
     never fires for realistic mixtures; its only use is degenerate
     single-component inputs.
     Fix: clarify comment or raise threshold to, say, 1e-9 to make the
     optimisation useful for trace components (<0.001 molar fraction).

N-10. No loading spinner or busy cursor during composition Apply
      File : ui/gui.py _apply_composition (line 800)
      Problem: calc_bwr_mixture(), calc_kappa(), and calc_mixture_thermo()
      all run synchronously in the event loop when "Apply composition" is
      clicked. For a 35-component mixture this is fast (~1 ms on modern
      hardware), but there is no visual feedback to indicate the button
      was registered.
      Fix: this is low-priority but could change button text to
      "Applying…" and restore it in an after(0, ...) callback.

POSITIVE OBSERVATIONS (things that work well)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

+ Hybrid bisection + Newton-Raphson density solver (bwrs.py lines
  154–160) is a significant improvement over pure bisection — NR steps
  are accepted only when they stay within the bracket, making it both
  robust and fast.

+ Thermal expansion correction is applied before beta/diameter range
  checks in calc_mass_flow(), which is metrologically correct.

+ Thread safety in the test runner: threading.Thread + self.after(0, ...)
  pattern is correct. stdout is redirected in the worker thread and
  restored in a finally block. UI updates are posted back to the event
  loop safely.

+ ANSI colour stripping in _display_test_output() (line 705) ensures
  the GUI shows clean text regardless of whether the validation code
  emits escape sequences.

+ calc_bwr_mixture() precomputes all (v_sq, v_cb, k_pair) and the six
  cube-root dicts once per call, avoiding redundant pow() calls inside
  the N² and N³ loops.

+ Comprehensive validation suite covers density (two temperatures),
  viscosity, Z-factor, molar mass, and Qm for all 9 device types across
  8 compositions, plus ISO 5167 negative tests and monotonicity checks.

+ Expansibility factor ε uses the exact isentropic formula for
  nozzles/Venturi tubes and the ISO 5167-2 linear approximation for
  orifice plates — consistent with the standard.
